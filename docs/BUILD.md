# Building

Prerequisites, per-platform builds, the test entry points, CI, and the release
checklist.

## Prerequisites

- **Rust** via [rustup](https://rustup.rs), stable toolchain — all platforms.
- **macOS app:** Xcode (full app; the SwiftUI package macros need its
  plugin) or CommandLineTools. If Xcode is installed but `xcode-select`
  points at the CLT, export
  `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer` so SwiftPM uses
  Xcode's toolchain. The Swift package targets macOS 13 and the Rust library
  is built with `MACOSX_DEPLOYMENT_TARGET=13.0`.
- **Windows app:** Visual Studio Build Tools with the MSVC C++ workload (the
  `windows` crate and `eframe`/`egui` need a C toolchain), plus Rust via
  rustup.

## macOS

```sh
./scripts/build-macos.sh            # release
./scripts/build-macos.sh --debug    # debug
open dist/FlowLink.app
```

What the script does, in order:

1. Exports `MACOSX_DEPLOYMENT_TARGET=13.0` and prefers
   `/Applications/Xcode.app/Contents/Developer` when present, then runs
   `cargo build -p flowlink-ffi` (`--release` unless `--debug`).
2. Copies `rust/target/<cfg>/libflowlink_ffi.a` to `macos/Vendor/` and the
   header to `macos/Sources/CFlowLinkCore/include/flowlink.h`.
3. Runs `swift build -c <cfg>` inside `macos/`.
4. Assembles `dist/FlowLink.app` from the built executable,
   `scripts/Info.plist`, a `PkgInfo`, and an `.icns` generated by
   `scripts/make-icon.swift` + `iconutil` (skipped if unavailable).
5. Ad-hoc codesigns the bundle (`codesign --sign -`); a failure is reported
   as a warning and the app still runs, but TCC permissions will re-prompt.

Running from source (`swift run FlowLink` in `macos/`) works for
development, but **launch at login requires the app bundle**: the Settings
toggle uses `SMAppService.mainApp`, which errors out with "run the app from
an .app bundle" otherwise.

Configuration, identity and logs live in
`~/Library/Application Support/FlowLink` (`config.json`, `identity/`, `logs/`).

## Windows

From the `rust` directory (PowerShell):

```powershell
cargo build --release -p flowlink-win
.\target\release\flowlink-win.exe
```

The Windows shell links `flowlink-core` directly (no C ABI involved) and
uses Win32 low-level hooks for capture, `SendInput` for injection, the
`windows` crate for platform APIs, `arboard` for the clipboard, and
`tray-icon` + `egui` for the tray and settings UI. Normal use needs no
elevation; see PLATFORM-LIMITS.md for what that means around elevated
windows.

- **Launch at login** is a Settings toggle that writes/removes an
  `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` entry. The installed
  command line includes `--autostart`, which starts the app hidden in the
  tray rather than showing the window.
- Config, identity and logs live in `%APPDATA%\FlowLink`.

Platform notes for the Windows shell are maintained in
`rust/crates/flowlink-win/`; prefer those sources over this summary if the
two ever disagree.

### UI preview mode (any platform)

The egui application is deliberately cross-platform: the window can be built
and run on macOS/Linux with no-op platform integrations. This is how the
Windows design is kept identical to the macOS one — both shells share the
same tokens (`theme.rs` mirrors the SwiftUI design system) and the Windows
pages can be inspected and screenshotted without a Windows machine:

```sh
cd rust
cargo run -p flowlink-win -- \
  --config-dir /tmp/flowlink-preview --preview-page server \
  --screenshot /tmp/server.png          # renders one frame, writes PNG, exits
```

| Flag | Meaning |
| --- | --- |
| `--config-dir <dir>` | isolated config/identity/logs directory |
| `--preview-page server\|client\|settings` | skip onboarding and open that page (server previews also start the engine so a real pairing code and QR are shown) |
| `--preview-theme light\|dark` | force a theme instead of the system one |
| `--screenshot <file>` | after ~1.5 s (engine settled) capture one frame, write it as PNG, quit |

On Windows itself these flags are harmless and can also be used for
screenshot-driven UI tests.

## Testing

```sh
./scripts/test.sh
```

runs, with `DEVELOPER_DIR` handled the same way as the build script:

```sh
(cd rust  && cargo test --workspace)   # unit tests + e2e_pairing.rs
(cd macos && swift test)               # FlowLinkKit tests (needs the built
                                       # static library in macos/Vendor)
```

If you only changed Swift code, `cargo build -p flowlink-ffi` +
`cp` of the library/header is enough to refresh `macos/Vendor` before
`swift test` (that is exactly what the macOS CI job does).

## CI

`.github/workflows/ci.yml` defines three jobs:

| Job | Runner | Steps |
| --- | --- | --- |
| `rust-core` | matrix: `macos-latest`, `windows-latest` | `cargo fmt --check` (advisory), `cargo clippy -D warnings` (advisory), `cargo test --workspace` (required) |
| `macos-app` | `macos-latest` | build `flowlink-ffi`, copy static lib + header, `swift test`, `./scripts/build-macos.sh`, upload `dist/FlowLink.app` as artifact `FlowLink-macos` |
| `windows-app` | `windows-latest` | `cargo check --workspace`, `cargo build --release -p flowlink-win`, upload `rust/target/release/flowlink-win.exe` as artifact `FlowLink-windows` |

The format and clippy steps are deliberately `continue-on-error: true`; the
test suite is the gate.

## Release checklist

1. **Bump the version** in `rust/Cargo.toml` (`[workspace.package]
   version`, inherited by all crates) and in `scripts/Info.plist`
   (`CFBundleShortVersionString`, and `CFBundleVersion` if you increment
   build numbers). Windows executables pick the version up from the
   workspace.
2. **Rebuild both artifacts** on their platforms (`scripts/build-macos.sh`,
   `cargo build --release -p flowlink-win`) and run `./scripts/test.sh`.
3. **Smoke-test a clean install:** fresh config directory, pair two devices,
   verify version/fingerprint shown in both UIs matches, check the clipboard
   limit and both reconnect paths (kill Wi-Fi on the client; relaunch the
   server).
4. **Sign and notarize (production, optional).** Ad-hoc builds are fine for
   internal use, but for distribution sign with a Developer ID Application
   certificate including the hardened runtime and timestamp, then notarize
   with `xcrun notarytool submit --wait` and `xcrun stapler staple
   dist/FlowLink.app`. For Windows, sign `flowlink-win.exe` with your
   Authenticode certificate if you distribute it publicly.
5. **Mind TCC on macOS.** Accessibility/Input Monitoring grants are tied to
   the code signature. A stable Developer ID signature keeps grants across
   updates; ad-hoc rebuilds require users to re-grant manually (the Settings
   screen links to the pane and detects the change). Mention this in release
   notes when the signing identity changes.
